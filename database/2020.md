# Database — 2020

## Lendf.Me
- Date: 2020-04 | Chain: Ethereum | Class: reentrancy (ERC777 tokensToSend hook)
- Mechanics: Lendf.Me's MoneyMarket did not guard against ERC777 hook reentrancy. The attacker registered itself as an ERC777TokensSender implementer, supplied imBTC, then withdrew; the tokensToSend callback (triggered by the contract's own token transfer during supply) called withdraw(type(uint).max) before internal accounting was updated, draining the pool. The PoC supplies all but 1 wei, then supplies 1 wei to trigger the hook which reenters withdraw, so the attacker walks away with both the borrowed balance and the pool's imBTC.
- Lesson: Any token with transfer hooks (ERC777, ERC1155 batch, TUSD) can reenter your logic mid-accounting — treat token callbacks as untrusted code and apply reentrancy guards/CEI even where no ETH is involved.

## Uniswap V1 — uniswap-erc777.sol
- Date: 2020-04 | Chain: Ethereum | Class: reentrancy (ERC777 tokensToSend hook, state-after-call price update)
- Mechanics: Uniswap V1's tokenToEthSwapInput computed the sell price from stale reserves and updated balances only after the token transfer. Using imBTC (ERC777), the attacker's tokensToSend callback re-entered tokenToEthSwapInput a second time before reserves were updated, selling the same 823,084 imBTC twice at nearly the same price and draining ~34 ETH from the pool. The PoC first swaps 1 ETH for imBTC to set up the balance, then approves and triggers the double-sell.
- Lesson: Never rely on post-transfer state updates for pricing — token callbacks (ERC777) let an attacker re-execute a swap before reserves/balances reflect the first trade.

## Balancer
- Date: 2020-06 | Chain: Ethereum | Class: oracle manipulation / deflationary-token accounting mismatch
- Mechanics: The STA token burns 1% on every transfer, so Balancer's recorded pool balance diverged from the actual balance. After a dYdX flash loan of WETH, the attacker repeatedly swapped WETH→STA and STA→WETH while calling gulp() to resync the STA balance, driving the recorded STA balance down to ~1 wei, which made the spot price of STA astronomically high. The attacker then sold 1 STA per swap for WETH, gulping after each trade to keep the price high across 20 swaps, repaying the flash loan with profit.
- Lesson: When a pool holds a fee-on-transfer or deflationary token, its internal balance bookkeeping drifts from reality and becomes manipulable — verify received amounts and never let attackers force resyncs (gulp) that amplify the divergence.

## Bancor
- Date: 2020-06 | Chain: Ethereum | Class: access-control (public safeTransferFrom)
- Mechanics: Newly deployed Bancor contracts exposed safeTransferFrom as a public function. Since any user who had previously approved those contracts could have their tokens pulled, the attacker simply called safeTransferFrom(token, victim, attacker, victim's full balance) and drained the victim's BNT pool tokens. The PoC demonstrates the theft by calling the public function directly with the victim's allowance.
- Lesson: Any public function that moves tokens on behalf of a third party using their allowance is a transfer-from-anyone primitive — audit every public surface for allowlist/msg.sender checks.

## Opyn
- Date: 2020-08 | Chain: Ethereum | Class: access-control / business-logic (double-exercise of oTokens)
- Mechanics: Opyn's exercise() accepted a vault array and moved ETH collateral to an attacker-designated address without tracking which oTokens had been exercised, allowing the same put options to be exercised twice. The attacker minted oTokens with a small amount of USDC collateral, then called exercise with the same msg.value and a two-element vault array, delivering ETH to two vaults from one payment, and pulled the underlying via removeUnderlying() for a ~$370k profit.
- Lesson: When a function processes a batch of objects against one payment/asset, check for duplicate entries and per-item consumption — missing double-spend accounting in exercise paths is a classic options-protocol killer.

## bZx
- Date: 2020-09 | Chain: Ethereum | Class: rounding / accounting (self-transfer token duplication)
- Mechanics: bZx's loan token transfer logic did not handle self-transfers correctly: transferring tokens to yourself credited the balance without zeroing the sender's balance first (or vice versa), so each self-transfer effectively doubled the balance. The attacker minted iETH with 200 ETH, looped self-transfers 4 times to inflate the balance ~16x, then called burnToEther to redeem far more ETH than deposited, repaying the simulated flash loan and profiting.
- Lesson: Self-transfers (from == to) are a cheap fuzz target in any token/accounting system — credit/debit ordering that works for distinct parties can double-count when sender and receiver coincide.

## Harvest Finance
- Date: 2020-10 | Chain: Ethereum | Class: oracle manipulation (Curve pool imbalance via flash loan)
- Mechanics: The attacker flash-loaned USDC and USDT from Uniswap V2 pairs, then swapped back and forth through the Curve y pool (exchange_underlying) while depositing into and withdrawing from Harvest's fUSDC vault, exploiting the fact that Harvest priced its vault shares using the manipulable Curve pool price. Repeating this 6 times skewed the Curve USDC/USDT price, letting the attacker withdraw more USDC/USDT from the vault than deposited. The PoC repays both flash loans with ~0.3% fee and keeps the profit.
- Lesson: Vault share pricing or withdrawal value derived from a spot AMM price the attacker can swing with flash loans is oracle manipulation — price deposits/withdrawals from a manipulation-resistant source.

## Pickle Finance
- Date: 2020-11 | Chain: Ethereum | Class: access-control / arbitrary call (unvalidated jar contracts)
- Mechanics: Pickle's Controller.swapExactJarForJar accepted attacker-supplied jar contracts without validating their token()/transfer() behavior. The attacker passed two FakeJar contracts whose token() returns cDAI, and through CurveLogic.add_liquidity chained arbitrary calls: withdrawAll() on the pDAI strategy, earn() on pDAI (which routed funds through the fake jar's deposit() that transfers to tx.origin), and withdraw(cDAI). The attacker-controlled fake token/jar implementations funneled ~20M DAI out of the pDAI jar to the attacker.
- Lesson: Any function accepting a contract address as a parameter (jar, curve, adapter) must validate what it points to — unvalidated external calls plus attacker-supplied contracts equals arbitrary execution.

## Cover Protocol
- Date: 2020-12 | Chain: Ethereum | Class: infinite-mint / reward-accounting (pool reward claim manipulation)
- Mechanics: The Cover/Blacksmith reward contract miscalculated the COVER rewards a user could claim — depositing BPT (a Balancer pool token) then calling claimRewards minted rewards without properly tracking the deposit snapshot, letting an attacker mint COVER far beyond the legitimate amount. The PoC deposits ~15,255 BPT and claims, showing a COVER balance gain after claimRewards.
- Lesson: Reward/mining contracts must snapshot user state and recompute accrued rewards against time and staked amount on every deposit/claim — missing accrual updates let a single deposit claim repeatedly at inflated rates.
