Methodology

The full smart-contract
audit process

Every step of an audit, in order — from the first scope question to the final report. Each step explains what is done, how, why it matters, and what it produces.

Step 1

Scoping & rules of engagement

What: Define the target: the exact commit/tag, the deployed addresses, the chain(s), the in-scope assets, and the program's impact list and severity definitions.

How: Read the program page and prior audits; pin the code at the audited commit (worktree per tag).

Why: Severity is judged against the program's OWN impact list — a "critical" elsewhere may be a Medium here.

Produces: A one-page scope card: target, addresses, commit hash, rules, severity mapping.

Step 2

Reconnaissance — deployed vs. repo delta

What: Compare what was audited (or what the repo claims) with what is actually deployed.

How: Pin the fork, fetch deployed bytecode, compile the audit-era source with the same solc settings, strip CBOR metadata, and diff. Establish a byte-identical control match first, then diff the rest.

Why: The highest-yield class on live programs is "the audits reviewed something else" — guards removed, constants changed, upgrades deployed.

Produces: A delta report: identical / metadata-only / real divergence, per contract.

Step 3

Plain-English vocabulary & architecture map

What: Describe the protocol in plain English before reading code: every actor, every asset, every action, every fee.

How: Walk the docs + interfaces; draw the module graph (who calls whom, who holds what).

Why: If you cannot explain the system simply, you cannot tell where the assumptions hide — and assumptions are where the bugs live.

Produces: A vocabulary sheet + module diagram used in the final report.

Step 4

The money map (accounting-first)

What: Enumerate every tracked total, every function that writes it, and the asymmetry table: value moved without a matching write; tracked in one branch only; never tracked.

How: A table of (asset, state variable, writers, readers) + 5–15 invariants written as statements, e.g. "sum(userBalances) == totalSupply at all times".

Why: Most real exploits are accounting desyncs, not missing modifiers.

Produces: The invariant list — the backbone of the PoC phase.

Step 5

Twelve-lens manual review

What: Read the code through twelve lenses: accounting-desync, share/exchange-rate, temporal-cohort, liquidation-solvency, cross-chain-state, rounding-precision, ordering/MEV, DoS/griefing, access-trust, integration-assumptions, edge-states, flow-completeness.

How: One pass per lens over the same code — never one blurry read.

Why: Each lens catches a different bug family; a single read catches whichever family is loudest.

Produces: Candidate leads, each tagged with its lens.

Step 6

Cohort attacks & the Last-User-Out test

What: Attack the protocol's lifecycles in worst-case orderings, not its functions in isolation: everyone deposits, some attack mid-flow, everyone withdraws in the worst order.

How: For each invariant, write the adversarial sequence that tries to break it; always include the Last-User-Out test — after all others exit, is the last user paid in full?

Why: Sequenced flows reveal the desyncs single-call tests cannot see.

Produces: A list of concrete attack scenarios to fork-prove.

Step 7

Fork-proof each lead (krait rules)

What: Prove every candidate on a mainnet fork of the REAL deployed contracts — never mocks.

How: The PoC must assert HARM (victim balance before/after), not mechanism. Then the falsification gate: mutate the defective line to its correct form — if the exploit still succeeds, the PoC is theater and the lead is demoted. Tag every run: [POC-PASS] / [POC-UNPINNED] / [POC-FAIL].

Why: Green tests are hypotheses; pinned tests are evidence. This is what separates a finding from a story.

Produces: For each real finding: a pinned fork PoC with before/after balances.

Step 8

The five gates (no false positives)

What: Every surviving lead must pass all five gates before being reported:
1. Exploit economics derived by hand, twice, with a named victim and gainer.
2. Storage/offset claims verified against the compiler's conventions.
3. Live reachability on the deployed in-scope asset — no admin precondition, no future deploy.
4. Prior-art honesty, including unpublished prior submissions.
5. Honest severity per the program's own impact list.

Why: One false positive destroys a reputation faster than ten true findings build it.

Produces: A gate pass/fail table per lead.

Step 9

Severity & impact calibration

What: Assign severity from the economics, not the mechanism: how much a real victim loses, how easily, how recoverable.

How: Map to the program's tiers (typically Critical $50K–$2M+ / High $10–50K / Medium $2–10K / Low $0.5–2K) and state the worst realistic outcome, not the theoretical ceiling.

Why: Overclaiming severity is the fastest route to an invalid verdict.

Produces: A severity recommendation per finding with the loss math shown.

Step 10

The report

What: Write each finding as a self-contained case: Brief/Intro · Vulnerability Details (root cause, the exact lines, why the guard fails) · Impact (the named victim, the loss math, worst realistic outcome) · References (prior art, similar incidents from this archive).

How: Follow the platform's template exactly; include the pinned PoC; state the verification status (which of the five gates passed) in one line.

Why: Triage is busy — a report that reads like evidence gets paid.

Produces: The submission-ready report.
